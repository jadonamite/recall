The product-recall query for software

Toyota has run this query since the 1970s.

When a bad component lot turns up, a manufacturer runs the bill of materials upward — which sub-assemblies used it, which finished products used those, which owners to write to. Software borrowed the phrase “bill of materials” and never implemented the query that makes one useful. Recall does.

01 What every scanner does

A list tells you that you’re bleeding. Not where the wound is.

Run npm audit on anything real and you get hundreds of findings, unordered, each naming a package you have never heard of and did not install on purpose. There is no way to tell which single upgrade kills thirty of them, because a list has already thrown away the path. So people stop reading the output. That is alert fatigue, and it is the defining failure of this entire category of tool.

Same data, both ways. One of these you can act on.

02 The query no scanner can answer

Your package was just compromised. Who do you have to write to?

A scanner starts from your manifest, so it can only ever answer the consumer’s question. The maintainer’s question runs the other way, and it is the one an actual product recall asks: who shipped my part, by what chain, and which single upgrade closes the most of it.

Pick a real compromised package. Every number below is measured, not illustrative — the dependents are real published packages and real public applications, and the graph they come from is public and reproducible.

03 The other direction

Your lock file, collapsed.

Open the tool → to walk every chain, or clone the repo and run it against your own lock file. Resolution is exact and offline: Recall replays npm’s own node_modules lookup rules, so the nested copy of a package stays distinct from the hoisted one — the edge a flat scanner collapses and loses.

04 Why this is not a table

“Reaches” is not a distance.

Every question above is a path query. A relational schema answers them with recursive CTEs that fall over at depth; a vector store cannot express them at all, because similarity is not reachability — the compromised package is not like your app, it is inside it.

05 Before you believe any of it

    
The limits, stated first.

    

      Every tool in this category overclaims, which is precisely why nobody trusts them. So here
      is what Recall does not do.
    

    

      
    
        
  • It does not claim reachability. Recall proves a vulnerable version is in your
            tree and shows the chain. It does not claim the vulnerable function is ever
            called. That is a much harder problem, and blurring the two is how this category lost
            its credibility.
    • 
        
  • The shared graph is a judgement call, not a mirror of npm. It is ~150
            high-traffic seed packages with their full resolved trees, plus the committed lock
            files of a handful of public repositories. That is what
            the numbers above describe. Scanning your own lock file is unaffected — your tree is
            ingested whole, and it never joins the shared graph.
    • 
        
  • An upgrade is not always available. Sometimes the real fix is an
            overrides entry, and sometimes upstream has not shipped one at all.
            Recall tells you where the path enters; it does not promise the door opens.
    • 
        
  • CVSS v4 vectors are reported unrated. The v4 score is a lookup table, not a
            closed form. Running the v3 equation over a v4 vector produces a confident number
            that is simply wrong, so those stay UNRATED.
