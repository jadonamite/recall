The argument

Reverse dependency traversal on HydraDB

Point it at your own tree. Get the chains, not a list.

A scanner hands you a flat list of vulnerable packages. Recall runs the bill of materials upward instead — which package reaches the compromised one, by what chain, and which single upgrade severs the most paths. Every finding collapses onto the one direct dependency it entered through.

Toyota has run this query since the 1970s.

This runs against a shared HydraDB node, not your machine. The lock file — fetched from the repository you name, or pasted here — is resolved, traversed, and thrown away: the tree is written under a relationship type belonging to this one scan and deleted when the answer is sent, so nothing you scan joins the public graph or is visible to anyone else. The node sleeps when idle, so the first scan after a quiet spell waits about a minute for it to wake, and it runs one scan at a time.

    RECORDED

    This is a recorded scan, not a live one. Recall's traversal needs a Bolt connection to a HydraDB node and reads a lock file off disk, neither of which exists on a static host — so the scan below was run locally and its result published with the page. Nothing is trimmed or invented: it is exactly what npm run recall printed for this public repository's committed lock file, on . Clone the repo to run it against your own.

    01
    Resolve

    Your lock file already knows the exact tree. Recall recovers the edges by replaying npm’s own node_modules lookup rules, so the nested copy of a package stays distinct from the hoisted one.

    02
    Traverse upward

    Each vulnerable version becomes the source of a reverse traversal over DEPENDS_ON. The answer is not “you are affected” — it is the chain, hop by hop, from your project down to the compromised package.

    03
    Collapse

    Every chain enters through exactly one direct dependency. Group by that hop and a wall of findings becomes a short ordered list of upgrades — which is what a recall notice has always been.
